# Item-template store bootstrap

This note freezes the current authored item-template snapshot boundary for the bootstrap runtime.

## Scope

The item-template store is intentionally narrow. It currently owns only the metadata needed by the existing item slices:

- stack behavior: `stackable`, `max_count`, and `anti_stack`
- item restriction guards: `anti_sell`, `anti_drop`, `anti_give`, `anti_get`, `anti_male`, `anti_female`, `anti_warrior`, `anti_assassin`, `anti_sura`, `anti_shaman`, `anti_empire_a`, `anti_empire_b`, `anti_empire_c`, `anti_save`, `anti_pk_drop`, `anti_myshop`, `anti_safebox`, and `min_level`
- merchant pricing helpers and client-visible item flags: `shop_buy_price`, `shop_sell_price`, `refineable`, `save`, `sell_count_per_gold`, `stackable`, `slow_query`, `rare`, `unique`, `make_count`, `irremovable`, `confirm_when_use`, `quest_use`, `quest_use_multiple`, `log`, and `applicable`
- client-visible item refresh hints: `highlight`
- equipment routing/effects: `equip_slot` and `equip_effect`
- equipment visible appearance override: `appearance_vnum`
- consumable point and optional visual effects: `use_effect`
- authored use/transfer/acquisition/merchant/equipment/refine/storage rejection text: `use_reject_message`, `drop_reject_message`, `give_reject_message`, `pickup_reject_message`, `buy_reject_message`, `sell_reject_message`, `equip_reject_message`, `unequip_reject_message`, `refine_reject_message`, and `safebox_reject_message`
- client-visible display metadata for occupied-slot refreshes: `sockets` and `attributes`
- bootstrap ground-pickup reach metadata: `pickup_range`

This is not a complete legacy item proto system yet.

## File-backed snapshot contract

The file-backed JSON snapshot has one top-level object:

```json
{
  "templates": []
}
```

Each template must pass the current `internal/itemstore` validation before the runtime will load it:

- `templates` must be present as a JSON array; a missing field or explicit `null` fails closed instead of being treated as an implicit empty template set
- an intentionally empty authored snapshot is valid only as `"templates": []`, and the file-backed writer persists that deterministic empty array rather than `null`
- `vnum` must be non-zero
- `name` must be non-empty after trimming and must not contain embedded NUL bytes, so authored item names cannot be silently truncated or split on fixed-string/client display boundaries
- `max_count` must be non-zero and fit the current bootstrap client-facing count field (`<= 255`)
- `shop_buy_price`, when authored, must fit the legacy `uint32` template price carrier; larger values fail closed at store load/save before merchant catalog or derived sell-back arithmetic can truncate or overflow them
- `shop_sell_price`, when authored, must fit the current signed `PLAYER_POINT_CHANGE` carrier (`<= 2147483647`); larger values fail closed at store load/save before merchant sell-back arithmetic can truncate or overflow them. The current sell-back runtime treats non-zero `shop_sell_price` as the explicit per-unit sell credit before falling back to derived `shop_buy_price` / `sell_count_per_gold` behavior.
- `pickup_range`, when authored, overrides the first bootstrap ground-item pickup reach for item stacks dropped from that template, and also overrides the bootstrap gold-marker pickup reach when authored on the currency-marker template `vnum = 1`. It must be no larger than the current bootstrap cap (`10000` coordinate units); oversized values fail closed at store load/save. Omitted or zero `pickup_range` preserves the existing deterministic 300-unit pickup reach.
- `highlight`, when set, projects to the one-byte `ITEM_SET.highlight` field for selected-character inventory/equipment bootstrap and later template-backed full item refreshes
- `appearance_vnum`, when set on a template whose `equip_slot` is one of the current visible projected slots (`body`, `weapon`, `head`, or `hair`), replaces the equipped item instance `vnum` only for the `CHAR_ADDITIONAL_INFO.parts` / `CHARACTER_UPDATE.parts` appearance projection; it does not change `ITEM_SET.vnum`, item identity, stack/equip guards, or persisted carried/equipped item snapshots. It must fit the current `uint16` visible-parts carrier (`<= 65535`). Authoring it on non-equipment templates, on unprojected equipment slots such as `shield`, or above that carrier fails closed at item-template validation.
- `refineable`, `save`, `slow_query`, `rare`, `unique`, `make_count`, `irremovable`, `confirm_when_use`, `quest_use`, `quest_use_multiple`, `log`, and `applicable`, when set, project only to the owned `ITEM_SET.flags` bits `ITEM_FLAG_REFINEABLE`, `ITEM_FLAG_SAVE`, `ITEM_FLAG_SLOW_QUERY`, `ITEM_FLAG_RARE`, `ITEM_FLAG_UNIQUE`, `ITEM_FLAG_MAKECOUNT`, `ITEM_FLAG_IRREMOVABLE`, `ITEM_FLAG_CONFIRM_WHEN_USE`, `ITEM_FLAG_QUEST_USE`, `ITEM_FLAG_QUEST_USE_MULTIPLE`, `ITEM_FLAG_LOG`, and `ITEM_FLAG_APPLICABLE`; they are client-visible metadata in this slice and do not add runtime refine, save/durability, slow-query durability, ownership, uniqueness, make-count, quest-use, repeated quest-use, applicable-effect, or logging policy yet
- `refine_reject_message`, when non-empty on a template that is not authored as `refineable`, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned by the current fail-closed `REFINE` guard when the requested `pos` identifies exactly one matching carried inventory item. Omitted text preserves the older no-frame/no-mutation rejection, while NUL-containing text or text authored on a `refineable = true` template fails closed at item-template validation.
- `refine_info`, when non-empty on a `refineable` template, is the runtime source of truth for the first self-only refine-dialog preview emitted by `REFINE`: it must author a non-zero `result_vnum`, a non-negative `cost`, a `probability` in `0..100`, and at most five material rows, each with non-zero material `vnum` and positive `count`. The runtime copies this metadata into one `REFINE_INFORMATION_NEW` frame using the client request `type` / `pos` and the carried item's source `vnum`; it does not mutate inventory, equipment, quickslots, points, gold, peers, ground handles, or persistence, and it still does not own success/failure/result semantics. Authoring `refine_info` without `refineable`, with malformed result/cost/probability/material rows, or with more than five material rows fails closed at item-template validation.
- `confirm_when_use`, when authored on a carried consumable, is a fail-closed direct-use guard for the current bootstrap `ITEM_USE` / `/use_item` path: the template still loads and projects the client-visible flag, but the runtime refuses to consume the stack or apply `use_effect` until a later slice owns the confirmation request/ack choreography
- `quest_use`, `quest_use_multiple`, and `applicable`, when authored on a carried consumable, are fail-closed direct-use guards for the current bootstrap `ITEM_USE` / `/use_item` path: the template still loads and projects the client-visible flags, but the runtime refuses to consume the stack or apply `use_effect` until later quest/applicable item flows are owned
- `use_reject_message`, when non-empty on a carried-use template that also authors `use_effect` plus one owned direct-use rejection guard (`confirm_when_use`, `quest_use`, `quest_use_multiple`, `applicable`, `anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`, job/sex/empire anti flags, or `min_level`), is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned when `ITEM_USE` / `/use_item` rejects that carried item for that template-authored guard; because the guard prevents the use effect from applying, this feedback is emitted even when the hypothetical `use_effect.point_delta` would overflow or underflow the selected character's current point value if it were applied; when omitted, the runtime preserves the older no-frame/no-mutation direct-use rejection; NUL-containing text, text authored without `use_effect`, or text authored without one of those owned direct-use guards fails closed at item-template validation
- non-stackable templates must use `max_count = 1`; templates that author an `equip_slot` must also be non-stackable, so malformed stackable equipment metadata fails closed at item-template snapshot load/runtime boot instead of reaching equip, drag-to-item, carried-move, or visible item-refresh paths
- `anti_stack` is accepted as explicit transfer-guard metadata and, when set, fails closed in current use/equip/merge/drop/sell paths, including player-requested item drops, merchant sell-back credit calculation, and packet `SHOP SELL` / `SELL2`, rather than describing an alternate stackability mode
- `drop_reject_message`, when non-empty, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned by player-requested `ITEM_DROP` / `ITEM_DROP2` transfer-guard failures and selected-character job/sex/empire/level restriction failures; transfer guards still fall back to the deterministic text `"You cannot drop this item."` when omitted, while selected-character restrictions remain silent when this text is omitted; NUL-containing text or text authored without one of those owned drop rejection guards fails closed at item-template validation
- `give_reject_message`, when non-empty on a template that also authors `anti_give`, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned by the current fail-closed `ITEM_GIVE` guard when the request names a currently connected visible player target and the requested count is non-zero and not larger than the live carried stack, and by the current active-shell `EXCHANGE ITEM_ADD` guard before any display-only exchange item-add frame is emitted for that carried item; if a merchant window is active on the same socket, that `ITEM_GIVE` feedback closes the merchant window first with self `GC::SHOP END`; if the requester is paired in the bootstrap exchange shell, that `ITEM_GIVE` feedback closes the exchange shell first with self/peer `GC::EXCHANGE END`; no-shell exchange item-add attempts and zero-target, unknown/invisible-target, zero-count, or oversized-count give attempts still preserve the older no-frame/no-mutation rejection even for authored `anti_give` items; this does not implement recipient transfer, item removal, gold placement, merchant buy/sell, or trade finalization semantics, and omitted text preserves the older no-frame/no-mutation rejection; NUL-containing text or text authored without `anti_give` fails closed at item-template validation
- `pickup_reject_message`, when non-empty on a template that also authors an owned pickup rejection guard (`anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`, job/sex/empire anti flags, or `min_level`), is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned by template-backed ground pickup transfer/selected-character restriction failures, including owner-delivery pickup checks; when omitted, the runtime preserves the older deterministic inventory-full fallback text `"You have too many items."`; NUL-containing text, or text authored without one of those owned pickup rejection guards, fails closed at item-template validation and runtime boot
- `buy_reject_message`, when non-empty, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text appended after the current merchant-family `GC::SHOP INVALID_POS` companion when packet `SHOP BUY` rejects the resolved catalog item because the resolved template authors `anti_get` or an owned selected-character job/sex/empire/level restriction; `anti_get` keeps the deterministic fallback text `"The merchant will not sell this item to you."` when omitted, while selected-character guard rejections without authored text remain silent after `INVALID_POS`; NUL-containing text, or text authored without one of those owned merchant-buy guards, fails closed at item-template validation
- `sell_reject_message`, when non-empty, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text appended after the current merchant-family `GC::SHOP INVALID_POS` companion when packet `SHOP SELL` / `SELL2` rejects a carried item because the resolved template authors an owned merchant-sell transfer guard (`anti_get`, `anti_drop`, `anti_give`, `anti_sell`, or `anti_stack`) or an owned selected-character job/sex/empire/level restriction; `anti_sell` keeps the deterministic fallback text `"The merchant refuses to buy this item."` when omitted, while `anti_get` / `anti_drop` / `anti_give` / `anti_stack` and selected-character guard rejections without authored text remain silent after `INVALID_POS`; NUL-containing text, or text authored without one of those owned merchant-sell guards, fails closed at item-template validation
- `equip_reject_message`, when non-empty on an equippable template that also authors an owned selected-character restriction or equip-time transfer guard (`anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`, job/sex/empire anti flags, or `min_level`), is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned when slash or packet equipment equip rejects that carried item because the selected character/template guard disallows it; when omitted, the runtime preserves the older silent/no-frame fail-closed equip rejection; NUL-containing text, text authored on a non-equipment template, or text authored on equipment without one of those owned equip rejection guards fails closed at item-template validation
- `unequip_reject_message`, when non-empty on an `irremovable` equipment template, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned when slash or packet equipment unequip rejects that worn item because the template authors `irremovable`; when omitted, the runtime preserves the older deterministic fallback text `"You cannot remove this item."`; NUL-containing text, or `unequip_reject_message` authored on a template that is not both equippable and `irremovable`, fails closed at item-template validation
- `safebox_reject_message`, when non-empty on a template that also authors `anti_safebox`, is the runtime source of truth for the self-only `CHAT_TYPE_INFO` rejection text returned by the current fail-closed `SAFEBOX_CHECKIN` guard when the requested position identifies exactly one matching valid carried inventory item; if an exchange shell is active on the same socket, that shell closes first with self/peer `GC::EXCHANGE END`; no safebox placement/open/password/money/persistence semantics are accepted yet. Omitted text preserves the older no-frame/no-mutation storage rejection, while NUL-containing text or text authored without `anti_safebox` fails closed at item-template validation.
- `anti_get` is a fail-closed acquisition guard for the currently owned bootstrap acquisition paths: ground pickup, template-backed merchant buy, and adjacent transfer-style mutations reject it before inventory, gold, quickslot, or persisted-state mutation
- `anti_save`, `anti_pk_drop`, `anti_myshop`, and `anti_safebox`, when set, project to the owned `ITEM_SET.anti_flags` bits `ANTI_SAVE`, `ANTI_PKDROP`, `ANTI_MYSHOP`, and `ANTI_SAFEBOX`; `anti_safebox` additionally enables the optional authored `safebox_reject_message` feedback guard above, but still does not add accepted safebox/storage mutation semantics yet
- template-backed merchant sell-back rejects live carried stacks whose current count already exceeds the resolved template-authored `max_count`, whose computed template-authored sell credit cannot fit the current signed `PLAYER_POINT_CHANGE` carrier, or whose resulting live gold would exceed that carrier before item refreshes, quickslot cleanup, gold mutation, or persisted-state mutation
- client-originated item quickslot bindings are template-backed for the item tuple when authored item metadata is available: `QUICKSLOT_ADD` with `type = item` must resolve valid item-template metadata for the targeted carried cell when the active authored template snapshot contains that item `vnum`, the template `vnum` must match the live item `vnum`, and the live stack count must not exceed the resolved template-authored `max_count`; if an authored snapshot is active and omits the targeted carried item `vnum`, the binding fails closed rather than falling back to unowned metadata. The deterministic missing-file/empty-store bootstrap fallback still permits legacy smoke-test/ad-hoc `vnum` item quickslot bindings under the older live-item validation path. Missing authored metadata, mismatched metadata, malformed metadata, over-template-max live stacks, locked/malformed live items, duplicate carried-cell occupancy, and empty cells fail closed before quickslot frames, persistence, or inventory mutation. Non-item quickslot edits remain governed by the quickslot tuple validation rules rather than item-template metadata.
- template-backed occupied-destination carried `ITEM_MOVE` swaps require valid authored source and target templates and reject either live cell when its count already exceeds that cell's authored `max_count` before refreshing either carried cell, deleting/retargeting item quickslots, or persisting the swap; accepted swaps project each item's authored display metadata into the resulting `ITEM_SET` for that item's new cell
- authored `equip_slot`, when present, must be one of the owned equipment slot names
- `min_level`, when present and non-zero, requires the selected character's persisted `level` to be at least that value before template-driven item actions are accepted
- `use_effect`, when present, must have a non-zero `point_type`, `point_index < 255`, a non-zero reversible signed `point_delta` (`-2147483648` is rejected because the runtime cannot safely reason about its inverse/range edges), an optional `consume_count` that defaults to `1`, non-empty trimmed `message`, an optional trimmed `info_message`, and an optional `special_effect_type`; both text fields reject embedded NUL bytes so template-authored client-visible placeholder text cannot be silently truncated on the fixed-string/chat boundary; positive deltas increase the authored point and negative deltas decrease it
- authored `use_effect.consume_count`, when non-zero, must be no greater than the template `max_count`; direct runtime item use also fails closed if the live stack has fewer than that authored count before point, stack, quickslot, or persistence mutation
- authored `use_effect.special_effect_type`, when non-zero, emits one self-only `SPECIAL_EFFECT` packet for accepted direct carried consumable use after point/item/quickslot refresh frames and before the self-only info-chat placeholder; values above the currently owned effect enum maximum (`25`) fail item-template validation until a later visual-effect policy slice broadens the owned range
- authored `use_effect.info_message`, when non-empty, is the runtime source of truth for the self-only bootstrap `CHAT_TYPE_INFO` placeholder after direct consumable use; when omitted, the runtime preserves the older fallback of using `use_effect.message` for that chat text so existing authored snapshots and the deterministic missing-file bootstrap fallback keep working
- `use_effect` is valid only on carried-use templates that do not author an `equip_slot`; equipment templates with `use_effect` are rejected so direct item use and equip side effects cannot both be authored on one bootstrap template
- `sockets`, when present, must contain exactly three signed 32-bit display values
- `attributes`, when present, must contain exactly seven `{type, value}` entries; an entry with `type = 0` must also use `value = 0` so malformed placeholder bonus rows fail closed
- `equip_effect`, when present, must have a non-zero `point_type`, `point_index < 255`, and a non-zero, reversible signed `point_delta` (`-2147483648` is rejected because its inverse cannot be represented as `int32`); positive deltas are bonuses and negative deltas are penalties
- `equip_effect` is only valid on templates that also author a valid `equip_slot`
- runtime pickup of a ground item backed by a valid authored equipment template keeps the item as carried inventory and never auto-equips it; the authored `equip_slot` remains routing metadata for later explicit equip requests, while pickup still enforces the same transfer and selected-character guards before inventory/persistence mutation
- runtime application of an `equip_effect` is fail-closed unless the selected character currently has a valid equipped item in that authored slot whose live `vnum` matches the same template; accepted effects apply the authored signed delta exactly as stored
- runtime removal of an `equip_effect` is fail-closed unless either the selected character currently has that matching equipped item or the caller supplies the valid just-removed item instance from that authored slot; this keeps unequip reversal template-backed without requiring the item to remain in equipment after the unequip mutation
- template-backed equip and unequip mutations also require the live carried/equipped item count to be non-zero and no greater than the authored `max_count`, so corrupt equipment snapshots cannot bypass template stack bounds just because equipment normally uses `max_count = 1`
- `irremovable`, when authored on equipment metadata, is a fail-closed unequip guard for the current template-backed equipment move path: explicitly authored snapshots reject dragging that worn item back into carried inventory before equipment, inventory, point, or persistence mutation
- duplicate `vnum` entries are rejected

- The store normalizes and persists deterministic JSON: the top-level `templates` collection is always written as an array, including `[]` for intentionally empty snapshots; template names, effect messages, optional consumable `info_message` text, optional `refine_reject_message`, `use_reject_message`, `drop_reject_message`, `pickup_reject_message`, `buy_reject_message`, `sell_reject_message`, `equip_reject_message`, `unequip_reject_message`, and `safebox_reject_message` text are trimmed, equipment slot names are normalized, merchant pricing metadata such as `shop_buy_price` / `shop_sell_price`, visible appearance override metadata such as `appearance_vnum`, optional `refine_info` rows and material rows, owned boolean flag metadata such as `refineable` / `save` / `slow_query` / `rare` / `unique` / `make_count` / `irremovable` / `confirm_when_use` / `quest_use` / `quest_use_multiple` / `log` / `applicable`, and owned anti-flag metadata such as `anti_save` / `anti_pk_drop` / `anti_myshop` / `anti_safebox` is written in a stable order, `use_effect.consume_count` is omitted only when it uses the default one-count behavior, `use_effect.info_message` is omitted when empty, `use_effect.special_effect_type` is omitted when zero, `refine_reject_message`, `use_reject_message`, `drop_reject_message`, `pickup_reject_message`, `buy_reject_message`, `sell_reject_message`, `equip_reject_message`, `unequip_reject_message`, and `safebox_reject_message` are omitted when empty, fixed socket/attribute arrays are written in owned packet order, and templates are sorted by `vnum`.

## Content-bundle summary projection

The loopback-only content-bundle summary read model repeats owned item-template guard metadata from resolved item templates into every template-backed summary row:

- top-level `item_templates`
- merchant `shop_catalogs[].entries`
- spawn-group `reward_drop_items`
- aggregate `reward_drops`

The direct-use projected fields are `confirm_when_use`, `quest_use`, `quest_use_multiple`, `applicable`, `use_effect`, and `use_reject_message`. The storage projected fields are `anti_safebox` and `safebox_reject_message`. The refine projected fields are `refineable` and `refine_reject_message`; expanded `refine_info` preview rows remain owned by the item-template store/runtime path rather than the content-bundle summary read model in this slice. This is operator/QA visibility only: it helps identify confirmation-, quest-, applicable-, storage-, refine-gated, and point-effect-bearing templates before import, but it does not add quest/applicable item execution, confirmation choreography, accepted safebox mutation semantics, or accepted refine result semantics.

The equipment projected fields are `equip_slot`, `appearance_vnum`, `irremovable`, `equip_effect`, `equip_reject_message`, and `unequip_reject_message`. These summary fields expose already-owned equipment routing, appearance projection, point-effect, and equip/unequip rejection metadata before import; they do not add new equipment slots, new appearance packet shapes, or broader equipment effects beyond the current template-backed equip/unequip runtime contract.

## Strict JSON hardening

The file-backed loader now rejects unknown JSON fields and trailing JSON values instead of silently accepting them. Template snapshots and item-template backup manifests must also be valid UTF-8 before JSON decoding; malformed bytes fail closed instead of being accepted through JSON replacement semantics.

This is a fail-closed authoring guard: if a snapshot contains unowned metadata such as a future effect field, multiple concatenated top-level JSON values, or non-UTF-8 authored/manifest data, the runtime must reject the snapshot rather than booting while ignoring, replacing, or only partially reading that metadata. This keeps item behavior template-backed only for fields the repository currently owns and tests.

## Bootstrap fallback

If the default item-template file is missing, the minimal runtime still uses the deterministic built-in bootstrap template snapshot. That fallback currently preserves local testing for:

- `11200` wooden sword equipment metadata
- `12200` practice blade equipment point metadata
- `27001` small red potion stack, merchant price, and use-effect metadata

Missing-file fallback is a bootstrap compatibility aid, not the final production item-data model.

Malformed snapshots, missing or `null` top-level template collections, invalid templates, duplicate `vnum` entries, stackable templates that also author `equip_slot`, snapshots with unknown JSON fields, and snapshots with trailing JSON values are fatal for runtime construction.

## Crash-temp residue cleanup

The file-backed item-template store now exposes a narrow crash-temp cleanup primitive for interrupted atomic writes:

- validation reports same-directory hidden `.item-templates-*.json` temp files as deterministic `crash_temp_count` / `crash_temp_files` residue without treating them as committed templates
- cleanup validates the committed `item-templates.json` snapshot first and fails closed if that snapshot is corrupt or invalid
- cleanup removes only same-directory `.item-templates-*.json` temp files; the committed snapshot and unrelated hidden files remain untouched
- cleanup syncs the item-template store directory after removals, then returns the post-cleanup validation summary

`gamed` exposes this as loopback-only operator tooling at `POST /local/item-templates/crash-temps/cleanup`. The endpoint accepts only an empty or whitespace-only body, rejects unexpected bodies and non-loopback callers, and is not a gameplay API.

## Migration-shaped export boundary

The authored item-template store still has a read-only projection for the current item-template database migration boundary (`0009_item_template_refine_info`, after the base `0005_item_template_state` schema and the additive `0006_item_template_safebox_reject_message` storage guard):

- the migration schema captures committed authored template metadata in `item_templates` plus child rows for display `sockets`, display `attributes`, optional `use_effects`, and optional `equip_effects`; additive item-template migrations add the optional `safebox_reject_message` column guarded by `anti_safebox` and the optional `refine_infos` / `refine_materials` child rows for template-authored refine-dialog preview metadata
- the projection validates through the same item-template snapshot contract used by runtime boot and store validation before emitting rows
- rows are deterministic by `vnum` and fixed display/effect/material positions so future backfill tooling can compare/export without relying on map iteration order
- a missing committed `item-templates.json` exports as an empty migration-shaped dataset instead of treating built-in bootstrap fallback templates as durable authored content
- `gamed` exposes this projection as loopback-only operator tooling at `GET /local/item-templates/exports/item-template-state`; the endpoint name is retained while the exported `migration_version` / `migration_name` identify the latest item-template boundary

This is still a schema/export contract only. It does not make item templates DB-backed, does not import or apply SQL, does not add accepted refine result semantics, and does not replace the file-backed runtime loader.

## Manifested backup, dry-run validation, and replacement restore

The file-backed item-template store now exposes a read/copy backup primitive for authored template snapshots:

- backup writes to an operator-supplied empty destination directory
- the destination must not be the active item-template store directory or nested under it, including through resolvable symlinks
- the committed `item-templates.json` snapshot is copied only after it passes the same strict load/validation contract used by runtime boot and `/local/item-templates/validate`
- same-directory `.item-templates-*.json` crash-temp residue is omitted from the backup payload
- a missing committed `item-templates.json` is backed up as an empty authored-template store, preserving the current deterministic runtime fallback rule without creating a synthetic committed snapshot
- successful backups write `item-template-backup-manifest.json` with a format marker, deterministic snapshot summary, copied filename, byte size, and SHA-256 checksum
- backup validation dry-runs that manifest and copied snapshot without mutating the active item-template store
- restore writes a validated manifest-backed backup into an empty active item-template store directory as a replacement primitive
- manifest validation rejects missing manifests, invalid UTF-8 manifest bytes, malformed/unknown/trailing manifest JSON, checksum or size drift, wrong snapshot filenames, untracked non-temp entries, and committed snapshots that fail the strict item-template loader
- restore refuses to run while the bootstrap runtime has connected live selected-character sessions, so future sessions can observe the restored template set without changing template semantics underneath already-entered players

`gamed` exposes this as loopback-only operator tooling:

- `POST /local/item-templates/backup` with `{"dst_dir":"/path/to/empty/backup"}`
- `POST /local/item-templates/backup/validate` with `{"src_dir":"/path/to/backup"}`
- `POST /local/item-templates/restore` with `{"src_dir":"/path/to/backup"}`

These endpoints are local bootstrap recovery tooling, not gameplay protocol and not a content merge API. Restore is a replacement primitive for an empty active store directory: it validates the backup first, writes the committed snapshot and a fresh manifest, reloads the runtime's in-memory template index for future sessions, and preserves the missing/empty authored-store fallback to built-in bootstrap templates. It is deliberately not a live gameplay reload; connected selected-character sessions must be drained before restore is accepted.

The durable account snapshot store and one-shot login-ticket store apply fail-closed item-instance validation before snapshots become newly authoritative. Persisted carried-inventory or equipment entries with malformed item instances, including zero-count item stacks, duplicate per-character item instance IDs across carried inventory/equipment, or duplicate equipped-slot occupancy, are rejected on both durable account save/load and login-ticket issue/load instead of being normalized into live bootstrap state. Duplicate carried-inventory slot occupancy is rejected on durable account save and one-shot login-ticket issue/load; raw durable account loads intentionally keep older duplicate-slot recovery fixtures readable, but those snapshots cannot be re-saved or issued as fresh login tickets unchanged.

# Item exchange bootstrap

This note freezes the first clean-room `EXCHANGE` boundary for the bootstrap item lane.

The goal is deliberately conservative:

- own the client packet layout before broader player-to-player trade is implemented
- reuse the owned shared server response packet layout for the first runtime exchange-window shell
- route the packet through the `GAME` phase without treating it as an unknown-header disconnect edge
- own the first two-party exchange-window shell (`START` / display-only `ITEM_ADD` / display-only `ITEM_DEL` / display-only `GOLD_ADD` / display-only `ACCEPT` / accept reset / accept-time requester plus already-accepted partner displayed-item and displayed-gold revalidation / second-accept receiver item-id collision, over-template-max compatible-stack, inventory-capacity, and gold-overflow precondition guards / `END`) without mutating inventory, equipment, quickslots, gold, ground items, or persisted account state until both sides have accepted under those frozen preconditions, and close that display shell before successful carried-item use, carried/equipment item moves, drag-to-item stack consolidation, carried-item drop refresh frames, or template-backed carried-drop rejection feedback is exposed for an item already shown in it
- keep richer trade-target eligibility beyond the owned exchange-distance gate plus the already-owned busy-window and transfer/warp teardown seams, rollback/audit policy, and any finalize/result choreography beyond the first mutual-accept mutation + shell close deferred until a later exchange/trade slice owns those semantics
- allow one active-shell template-authored guard response for already-owned transfer / selected-character rejection metadata on `ITEM_ADD` without implementing item transfer

This is not a completed exchange, trade, safebox, or player-shop system.

## Evidence

The TMP4-compatible client exposes `CG::EXCHANGE = 0x0508` on the main game socket. The client send helpers use one fixed client packet shape for exchange start, item add, item delete, gold add, accept, and cancel requests. The subheader selects the requested exchange action. Its `GC::EXCHANGE ITEM_DEL` receive path clears one exchange display slot from the receiver's self/peer exchange-side model, so this bootstrap slice treats `ITEM_DEL.arg1` as the currently owned display slot to clear. Its gold-add path uses the same `GC::EXCHANGE` family with `arg1` carrying the displayed gold amount, which this slice owns only as display state. Its accept receive path sets the self/peer exchange-window accepted indicator from `arg1`; the legacy server clears both accept indicators with `GC::EXCHANGE ACCEPT(arg1 = 0)` before accepted item/gold display changes, so this bootstrap slice owns that reset marker while still deliberately avoiding final trade mutation.

## Client packet

All packets use the standard frame envelope: `header uint16 LE`, `length uint16 LE`, followed by the payload.

### `CG::EXCHANGE` (`0x0508`)

Direction: client -> server.

Payload size is 9 bytes:

| Offset | Field | Type | Notes |
| --- | --- | --- | --- |
| 0 | `subheader` | `uint8` | exchange action selector |
| 1 | `arg1` | `uint32 LE` | target `vid`, gold amount, display/delete slot, or zero depending on subheader |
| 5 | `arg2` | `uint8` | item display slot for item-add requests (`0..11` for the current TMP4 exchange UI), otherwise zero/ignored |
| 6 | `pos` | packed `TItemPos` | `window_type uint8`, `cell uint16 LE`; meaningful for item-add requests |

The current owned exchange item-display surface has 12 slots. Runtime guard feedback for `ITEM_ADD` therefore treats `arg2 >= 12` as malformed for the current bootstrap exchange boundary and falls back to the ordinary no-frame/no-mutation rejection.

Total frame length is 13 bytes including the common `header` and `length` fields.

Current owned client subheaders:

| Name | Value | Current runtime policy |
| --- | ---: | --- |
| `START` | `0` | starts the current visible-peer exchange-window shell when the peer is connected and visible |
| `ITEM_ADD` | `1` | display-only item placement inside the current bootstrap exchange shell |
| `ITEM_DEL` | `2` | display-only removal inside the current bootstrap exchange shell |
| `ELK_ADD` | `3` | display-only gold placement inside the active shell when the requested amount is non-zero and not above the requester's live gold; otherwise `LESS_GOLD` or fail-closed |
| `ACCEPT` | `4` | accept marker inside the active shell after neither paired side has an open merchant/safebox/refine busy presentation, the requester's remembered item/gold display state still matches live state and, when the partner had already accepted, the partner's remembered display state also still matches live state and both receivers satisfy the currently frozen finalization preconditions; when that second accept succeeds, the shell finalizes the currently displayed item/gold transfer and closes |
| `CANCEL` | `5` | closes the current paired exchange-window shell |

The repository owns this client byte layout, the current visible-peer open/close shell, the first display-only `ITEM_ADD` / `ITEM_DEL` companions, the first display-only `ELK_ADD` companion, the first `ACCEPT` companion, the accept-marker reset emitted before accepted display changes, accept-time requester and already-accepted partner displayed item/gold revalidation, second-accept receiver item-id collision, over-template-max compatible-stack, inventory-capacity, and gold-overflow precondition guards, and the first mutual-accept finalization contract below. It now also owns the first exchange-distance eligibility gate for `START` and walk-away shell close (`ApproxDistance < 1000` on the same effective map), the requester-side open-merchant / open-safebox / open-refine-dialog PREVENT_TRADE_WINDOW start reject, and the partner-side open-merchant / open-safebox / open-refine-dialog busy-window rejection text. It does not yet own richer trade-target eligibility beyond that distance/merchant/safebox/refine busy gate, rollback/audit policy, or any finalize/result choreography beyond that first mutual-accept mutation + shell close.

## Server packet

### `GC::EXCHANGE` (`0x051C`)

Direction: server -> client.

The shared server exchange response frame uses one fixed payload shape for all currently documented server subheaders:

| Offset | Field | Type | Notes |
| --- | --- | --- | --- |
| 0 | `subheader` | `uint8` | server exchange action/status selector |
| 1 | `is_me` | `uint8` | non-zero when the response describes the receiver's own exchange side |
| 2 | `arg1` | `uint32 LE` | `vnum`, `gold`, accept flag, peer `vid`, display slot, or status-specific scalar |
| 6 | `arg2` | packed `TItemPos` | `window_type uint8`, `cell uint16 LE`; exchange item display positions currently use `RESERVED_WINDOW` |
| 9 | `arg3` | `uint32 LE` | count or status-specific scalar |
| 13 | `sockets` | `[3]int32 LE` | copied from item display metadata for `ITEM_ADD`, zero otherwise |
| 25 | `attributes` | `[7]{type uint8, value int16 LE}` | copied from item display metadata for `ITEM_ADD`, zero otherwise |

Total frame length is 50 bytes including the common `header` and `length` fields.

Current owned server subheaders:

| Name | Value | Current runtime policy |
| --- | ---: | --- |
| `START` | `0` | emitted for the current visible-peer open shell |
| `ITEM_ADD` | `1` | emitted for the current display-only item-add shell while no item ownership transfer is performed |
| `ITEM_DEL` | `2` | emitted for the current display-only item-removal shell while no item ownership transfer is performed |
| `GOLD_ADD` | `3` | emitted for the current display-only gold placement shell while no gold ownership transfer is performed |
| `ACCEPT` | `4` | display-only accepted marker for one side of the active shell |
| `END` | `5` | emitted for the current cancel/close shell |
| `ALREADY` | `6` | emitted self-only when `START` targets a visible connected peer that is already paired in the bootstrap exchange shell |
| `LESS_GOLD` | `7` | emitted self-only when an active-shell gold placement requests more than the requester's live gold, or when an accept attempt finds the requester's previously displayed gold is now above live gold |

The shipped runtime now emits `START`, display-only `ITEM_ADD`, display-only `ITEM_DEL`, display-only `GOLD_ADD`, first-side display-only `ACCEPT`, accept-marker reset packets with `arg1 = 0` before accepted item/gold display changes, self-only `LESS_GOLD`, `END`, and the narrow busy-target `ALREADY` response for the visible-peer exchange-window shell described below. `LESS_GOLD` is used both for over-budget gold display requests and for the current accept-time stale displayed-gold branch of the requester's display-state revalidation guard. Stale requester displayed carried items are rejected silently at accept time instead of emitting a finalization/result frame. When the paired partner had already accepted, the second accept also revalidates the accepted partner's remembered displayed items and displayed gold against the partner's current shared-world character state; partner drift rejects the second accept silently with no result frame and leaves the shell cancellable. The same second-accept seam now also checks the currently frozen receiver-side finalization preconditions before emitting any new accept marker: each receiver must have inventory capacity for the other side's displayed items under the loaded templates, and any incoming displayed gold must fit the receiver's current gold point-change carrier. Receiver precondition failures reject silently with no result frame and leave the shell cancellable. A first-side `ACCEPT` remains a presentation marker only; when the second accept passes those checks, the runtime owns the mutual-accept finalize below (item/gold transfer, quickslot clear, dual persistence, and shell `END`) without introducing a richer finalize/result packet family.

## Current runtime contract

`internal/game` decodes `EXCHANGE` while the session is already in `GAME` and routes it to a dedicated handler hook. The default handler denies the request with no response.

The shipped minimal runtime owns only a small in-memory exchange-window shell:

- `START` succeeds only when the requester owns a live `GAME` shared-world session above the bootstrap zero-HP floor, `arg1` identifies another connected visible player `VID`, that peer is within the owned exchange-distance gate (`ApproxDistance < 1000` on the same effective map), and neither player is already paired in this bootstrap exchange shell.
- A successful `START` returns one self-only `GC::EXCHANGE START` to the requester with `arg1 = target_vid` and queues one `GC::EXCHANGE START` to the visible target with `arg1 = requester_vid`.
- If `START` targets a visible connected player that is already paired, the requester receives one self-only `GC::EXCHANGE ALREADY`; the existing pair receives no frames and no exchange state changes.
- If `START` targets a visible connected player that is outside the owned exchange-distance gate, the request fails closed with no exchange frames and no pairing/display mutation.
- If the requester already has an open same-socket merchant window, `START` returns one self-only `CHAT_TYPE_INFO` with `You cannot trade while another trade window is open.`; no exchange frames are emitted, no pairing/display mutation occurs, and the merchant window is left open.
- If the requester already has an open same-socket bootstrap safebox presentation (`/open_safebox` flag from `item-storage-guard-bootstrap.md`), `START` returns the same self-only `CHAT_TYPE_INFO` with `You cannot trade while another trade window is open.`; no exchange frames are emitted, no pairing/display mutation occurs, and the safebox presentation remains open.
- If the requester already has an open same-socket refine-dialog presentation (`REFINE_INFORMATION_NEW` preview from `item-refine-bootstrap.md`), `START` returns the same self-only `CHAT_TYPE_INFO` with `You cannot trade while another trade window is open.`; no exchange frames are emitted, no pairing/display mutation occurs, and the refine dialog remains open.
- If `START` targets a visible connected player that currently has an open same-socket bootstrap merchant window, the requester receives one self-only `CHAT_TYPE_INFO` with `That player cannot trade right now.`; the busy partner receives no frames, no exchange pairing/display state is created, and the partner's merchant window remains open.
- If `START` targets a visible connected player that currently has an open same-socket bootstrap safebox presentation, the requester receives the same self-only `CHAT_TYPE_INFO` with `That player cannot trade right now.`; the busy partner receives no frames, no exchange pairing/display state is created, and the partner's safebox presentation remains open.
- If `START` targets a visible connected player that currently has an open same-socket refine-dialog presentation, the requester receives the same self-only `CHAT_TYPE_INFO` with `That player cannot trade right now.`; the busy partner receives no frames, no exchange pairing/display state is created, and the partner's refine dialog remains open.
- `CANCEL` succeeds only while the requester is currently paired in that shell.
- A successful `CANCEL` returns one self-only `GC::EXCHANGE END` to the cancelling player and queues one `GC::EXCHANGE END` to the paired player.
- If practice-mob retaliation drives either paired player's live bootstrap HP to `0` while the shell is open, the death edge closes the shell with the same `GC::EXCHANGE END` family: the dying owner receives one self-only `END`, the paired live peer receives one queued `END`, and the in-memory pairing/display state is cleared before later exchange requests can run.
- If either paired player relocates so `ApproxDistance` is no longer strictly below `1000` (or the peers no longer share an effective map), the runtime closes the shell with the same `GC::EXCHANGE END` family before later exchange requests can run: the mover receives one self `END`, the paired peer receives one queued `END`, and the in-memory pairing/display/accept state is cleared without inventory/equipment/quickslot/gold/persistence mutation.
- If same-socket exact-position transfer / warp rebootstrap begins while the requester is paired in this bootstrap shell (including same-map in-range destinations that would still satisfy the walk-away distance gate), the runtime closes the shell before the transfer rebootstrap burst is delivered: the transferring player receives one self-only `GC::EXCHANGE END` before the normal self transfer bootstrap / origin visibility frames, the paired peer receives one queued `GC::EXCHANGE END`, and the in-memory pairing/display/accept state is cleared without inventory, equipment, quickslot, gold, ground-item, or exchange trade mutation. When an open merchant window is also closed by that same transfer, the already-owned merchant `GC::SHOP END` precedes the exchange `END`. Later `ACCEPT` / mutual-accept finalize attempts against the torn-down shell fail closed with no frames.
- If same-socket `/quit`, `/logout`, or `/phase_select` begins while the requester is paired in this bootstrap shell, the runtime closes the shell before the lifecycle command completes: the command sender receives one self-only `GC::EXCHANGE END` before the command delivery or phase-transition frame, the paired peer receives one queued `GC::EXCHANGE END`, and the in-memory pairing/display/accept state is cleared without inventory, equipment, quickslot, gold, ground-item, or persisted-account mutation.
- If same-socket `/use_item <slot>` or packet `ITEM_USE` targets a carried inventory cell that is currently displayed in the requester's active exchange shell, the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory, quickslots, points, gold, and exchange display/accept state unchanged.
- If same-socket `/use_item <slot>` or packet `ITEM_USE` succeeds against a non-displayed carried item while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the item-use response burst is delivered: the item-use requester receives one self-only `GC::EXCHANGE END` before the slash or packet item-use frames, the paired peer receives one queued `GC::EXCHANGE END`, and the in-memory exchange pairing/display/accept state is cleared. The item-use mutation itself then follows the separately owned `item-use-bootstrap.md` persistence rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket `/use_item <slot>` or packet `ITEM_USE` returns template-authored `use_reject_message` feedback instead of mutating state, the runtime now closes the exchange shell before the self-only info-chat frame is delivered: the requester receives one self-only `GC::EXCHANGE END`, the paired peer receives one queued `GC::EXCHANGE END`, the requester then receives the authored `CHAT_TYPE_INFO` rejection, and carried inventory, quickslots, points, gold, ground handles, exchange item/gold displays, and persisted account snapshots remain unchanged.
- If same-socket carried-to-carried `ITEM_MOVE` or the local `/inventory_move <from> <to>` harness would change a currently displayed exchange carried cell (source or destination), the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory/quickslot/gold/exchange display state unchanged.
- If same-socket carried-to-carried `ITEM_MOVE` or the local `/inventory_move <from> <to>` harness succeeds against non-displayed carried cells while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the inventory refresh burst is delivered: the requester receives one self-only `GC::EXCHANGE END` before the item and quickslot refresh frames, the paired peer receives one queued `GC::EXCHANGE END`, and the in-memory exchange pairing/display/accept state is cleared. The carried-slot move itself then follows the separately owned `item-move-bootstrap.md` persistence and quickslot rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket carried-to-equipment `ITEM_MOVE` or `/equip_item` would equip a currently displayed exchange carried cell, or equipment-to-carried `ITEM_MOVE` / `/unequip_item` would land into a currently displayed exchange carried cell, the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory/equipment/quickslot/exchange display state unchanged.
- If same-socket carried-to-equipment or equipment-to-carried `ITEM_MOVE` succeeds against non-displayed carried cells while the requester is paired in this bootstrap shell, or the requester uses the local `/equip_item <from> <equip_slot>` or `/unequip_item <equip_slot> <to>` harness on non-displayed cells, the runtime closes the exchange shell before the equipment mutation refresh burst is delivered: the requester receives one self-only `GC::EXCHANGE END` before the item/equipment/appearance/quickslot refresh frames, the paired peer receives one queued `GC::EXCHANGE END` before any queued peer appearance update, and the in-memory exchange pairing/display/accept state is cleared. The equipment mutation itself then follows the separately owned item-move/equipment persistence and quickslot rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket equipment `ITEM_MOVE` or the local `/equip_item` / `/unequip_item` harness returns template-authored equipment rejection feedback instead of mutating state, the runtime now closes the exchange shell before the self-only info-chat frame is delivered. This covers selected-character/template-guarded equip rejection text and `irremovable` unequip rejection text: the requester receives one self-only `GC::EXCHANGE END`, the paired peer receives one queued `GC::EXCHANGE END`, the requester then receives the authored `CHAT_TYPE_INFO` rejection, and carried inventory, equipment, quickslots, points, ground handles, exchange item/gold displays, and persisted account snapshots remain unchanged.
- If same-socket `ITEM_USE_TO_ITEM` would change a currently displayed exchange carried cell (source or target), the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory/quickslot/exchange display state unchanged.
- If same-socket `ITEM_USE_TO_ITEM` stack consolidation succeeds against non-displayed carried cells while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the stack-merge refresh burst is delivered: the requester receives one self-only `GC::EXCHANGE END` before the item/quickslot frames, the paired peer receives one queued `GC::EXCHANGE END`, and the in-memory exchange pairing/display/accept state is cleared. The stack mutation itself then follows the separately owned `item-use-bootstrap.md` persistence rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket carried-item `ITEM_DROP` / `ITEM_DROP2` targets a currently displayed exchange carried cell, the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory/quickslot/gold/ground/exchange display state unchanged.
- If same-socket carried-item `ITEM_DROP` / `ITEM_DROP2` succeeds against a non-displayed carried item while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the drop response burst is delivered: the drop requester receives one self-only `GC::EXCHANGE END` before the item/quickslot/ground/ownership frames, and the paired peer receives one queued `GC::EXCHANGE END` before the normal visible ground add/ownership frames for that drop. The carried-item drop mutation itself then follows the separately owned `item-drop-pickup-bootstrap.md` persistence and temporary-ground-handle rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket carried-item `ITEM_DROP` / `ITEM_DROP2` returns template-backed transfer-guard or selected-character rejection feedback while the requester is paired in this bootstrap shell, the runtime now closes the exchange shell before that self-only info-chat frame is delivered: the requester receives one self-only `GC::EXCHANGE END`, the paired peer receives one queued `GC::EXCHANGE END`, the requester then receives the authored or fallback `CHAT_TYPE_INFO` rejection, and carried inventory, quickslots, points, gold, ground handles, exchange item/gold displays, and persisted account snapshots remain unchanged.
- If same-socket `ITEM_PICKUP` succeeds while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the pickup response burst is delivered: the requester receives one self-only `GC::EXCHANGE END` before `GC::ITEM_GROUND_DEL`, item refresh, point-change when gold is picked up, and `GC::ITEM_GET` frames; the paired peer receives one queued `GC::EXCHANGE END` before any queued visible-ground delete frame. The pickup mutation itself follows the separately owned `item-drop-pickup-bootstrap.md` persistence and temporary-ground-handle rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket `ITEM_PICKUP` returns template-backed pickup rejection feedback or the inventory-full fallback while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before that self-only info-chat frame is delivered: the requester receives one self-only `GC::EXCHANGE END`, the paired peer receives one queued `GC::EXCHANGE END`, the requester then receives the authored or fallback `CHAT_TYPE_INFO` rejection, and carried inventory, quickslots, points, gold, ground handles, exchange item/gold displays, and persisted account snapshots remain unchanged.
- If same-socket merchant `SHOP SELL` or `SHOP SELL2` targets a currently displayed exchange carried cell, the request fails closed with no frames, leaves the exchange shell open, and leaves live/persisted inventory/quickslot/gold/exchange display state unchanged.
- If same-socket merchant `SHOP BUY`, or merchant `SHOP SELL` / `SHOP SELL2` of a non-displayed carried cell, succeeds while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the merchant transaction refresh burst is delivered: the requester receives one self-only `GC::EXCHANGE END` before the item refresh / gold point-change frames, and the paired peer receives one queued `GC::EXCHANGE END`. The merchant transaction itself follows the separately owned `npc-shop-transaction-bootstrap.md` inventory, quickslot, gold, and persistence rules; no exchange item/gold transfer or finalization result is produced.
- If same-socket `REFINE` returns a template-authored non-refineable rejection chat or a template-authored `REFINE_INFORMATION_NEW` preview while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the refine feedback frame is delivered: the requester receives one self-only `GC::EXCHANGE END` before the self refine chat/preview frame, and the paired peer receives one queued `GC::EXCHANGE END`. The refine path remains mutation-free and follows `item-refine-bootstrap.md`; no exchange item/gold transfer or finalization result is produced.
- If same-socket `ITEM_GIVE` returns a template-authored `anti_give` / `give_reject_message` self-only rejection while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the item-give feedback frame is delivered: the requester receives one self-only `GC::EXCHANGE END` before the self rejection chat, and the paired peer receives one queued `GC::EXCHANGE END`. The item-give path remains mutation-free and follows `item-give-bootstrap.md`; no exchange item/gold transfer or finalization result is produced.
- If same-socket `QUICKSLOT_ADD`, `QUICKSLOT_DEL`, or `QUICKSLOT_SWAP` succeeds while the requester is paired in this bootstrap shell, the runtime closes the exchange shell before the self-only quickslot refresh frame(s) are delivered: the requester receives one self-only `GC::EXCHANGE END`, the paired peer receives one queued `GC::EXCHANGE END`, and the accepted quickslot edit then follows `quickslot-bootstrap.md` persistence rules. No exchange item/gold transfer or finalization result is produced.

Until both sides have accepted under the frozen preconditions, the shell remains display-only: it performs no inventory, equipment, quickslot, gold, ground-item, or persisted-account mutation. It emits display-only exchange `ITEM_ADD` responses for valid carried items in the active shell, display-only `ITEM_DEL` responses for occupied display slots in that shell, display-only `GOLD_ADD` responses for non-zero active-shell gold placement requests that do not exceed the requester's live gold, first-side display-only `ACCEPT` responses for active-shell accept requests whose requester-side remembered displayed items and gold still match live state, and one self-only `LESS_GOLD` response when an accept attempt finds that the requester's own previously displayed gold amount no longer fits the requester's current live gold. Second-accept attempts that fail partner revalidation or receiver finalization preconditions also stay mutation-free and leave the shell cancellable.

The display-only `ITEM_ADD` path is accepted only when the requester is already paired in the bootstrap exchange shell and the requested display slot is in the current owned `0..11` range. The source must be a carried inventory cell, resolve through the loaded item-template snapshot, and contain exactly one unlocked, unequipped, well-formed item whose `vnum` and count fit the resolved template. The resolved template must also be usable by the selected character and must not author the current transfer guards (`anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`). On success, the requester receives one direct `GC::EXCHANGE ITEM_ADD` with `is_me = 1`, and the paired peer receives one queued `GC::EXCHANGE ITEM_ADD` with `is_me = 0`. Both packets carry `arg1 = item.vnum`, `arg2 = RESERVED_WINDOW + display_slot`, `arg3 = item.count`, and the template-authored `sockets` / `attributes` display arrays. The selected carried item is not removed from inventory, no quickslot changes are made, no gold changes, and no account snapshot is persisted. While that carried item identity remains displayed, same-socket mutations that would change that live item (`ITEM_USE`, carried `ITEM_MOVE` / equip/unequip, `ITEM_USE_TO_ITEM`, `ITEM_DROP` / `ITEM_DROP2`, and merchant sell of that cell) fail closed with no frames and leave the exchange shell open; `ITEM_DEL`, cancel/close, death/walk-away/lifecycle teardown, and successful mutual-accept finalize clear that display lock.

Each side owns its own display-slot namespace in this bootstrap shell. Reusing the same display slot for a second `ITEM_ADD` from the same side fails closed with no frames and no mutation. Reusing the same carried item instance in a second display slot from the same side also fails closed with no frames and no mutation, so the current display-only shell cannot show one live item identity twice at once. `ITEM_DEL` succeeds only when the requester is currently paired and `arg1` identifies one occupied display slot in the requester's own namespace. A successful `ITEM_DEL` returns one direct `GC::EXCHANGE ITEM_DEL` with `is_me = 1`, queues one peer `GC::EXCHANGE ITEM_DEL` with `is_me = 0`, carries the cleared display slot in `arg1`, and frees that in-memory display slot plus its carried item identity so a later display-only `ITEM_ADD` can reuse either. If either side had previously displayed `ACCEPT`, the accepted-marker reset packets described below are emitted before the `ITEM_DEL` clear frame for each receiver. Cancelling or closing the exchange clears the in-memory display-slot occupancy together with the paired shell.

The display-only `GOLD_ADD` path is accepted only when the requester is currently paired in the bootstrap exchange shell and `arg1` is non-zero. When `arg1` is less than or equal to the requester's current live gold, the requester receives one direct `GC::EXCHANGE GOLD_ADD` with `is_me = 1` and the paired peer receives one queued `GC::EXCHANGE GOLD_ADD` with `is_me = 0`; both packets carry the displayed gold amount in `arg1`, and the runtime remembers that displayed amount for later accept-time revalidation. If either side had previously displayed `ACCEPT`, the gold display response first includes the reset packets described below. When `arg1` is greater than the requester's current live gold, the requester receives one direct `GC::EXCHANGE LESS_GOLD` and the peer receives no frame. Both outcomes leave live gold and persisted account snapshots unchanged.

The display-only `ACCEPT` path is accepted only when the requester is currently paired in the bootstrap exchange shell, neither paired side currently has an open same-socket bootstrap merchant window / safebox presentation / refine-dialog presentation, and the requester's remembered display state still matches live state. If the requester currently has one of those busy presentations open, `ACCEPT` fails closed with one self-only `CHAT_TYPE_INFO` using the same requester busy text already owned by exchange `START` (`You cannot trade while another trade window is open.`): no self accept marker, no peer accept marker, no finalization/result frame, no mutation, and the shell remains cancellable while the busy presentation stays open. If only the paired partner currently has one of those busy presentations open, `ACCEPT` fails closed with one self-only `CHAT_TYPE_INFO` using the same partner busy text already owned by exchange `START` (`That player cannot trade right now.`), with the same no-accept-marker / no-mutation / still-cancellable contract. When both sides are busy, the requester busy text wins, matching the local-first `START` busy ordering. The current selected-character identity must still match the shared-world exchange owner by character id, `VID`, and normalized name. For displayed carried items, each remembered display slot must still resolve through the current loaded item-template snapshot and exactly one live carried inventory item with the same item instance id, `vnum`, count, and carried slot; the item must remain unlocked, unequipped, well-formed, must not exceed the currently loaded template `max_count`, must still pass selected-character and transfer-guard template restrictions (`anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`), and the live carried inventory snapshot must not contain duplicate carried-slot occupancy or duplicate item instance ids. If this requester item revalidation fails, `ACCEPT` fails closed silently: no self accept marker, no peer accept marker, no finalization/result frame, no mutation, and the shell remains cancellable. If the requester previously displayed gold, the displayed amount must also still be less than or equal to the requester's current live gold. When the paired partner had already accepted, the same accept attempt also revalidates the partner's remembered displayed carried items and displayed gold against the partner's current shared-world character snapshot before emitting any new accept marker. A stale accepted-partner displayed carried item or stale accepted-partner displayed gold rejects this second accept silently: no self accept marker, no peer accept marker, no `LESS_GOLD`, no finalization/result frame, no mutation, and the shell remains cancellable. Before a second accept displays a new marker or mutual-accept finalize plan, the runtime also re-checks that neither paired side currently has an open merchant / safebox / refine busy presentation, then evaluates currently frozen receiver-side finalization preconditions: incoming displayed items must not reuse any item instance id already present in the receiver's carried inventory or equipment; any existing compatible receiver stack considered for a merge must itself be well-formed and no greater than the same loaded template's `max_count`; each incoming displayed item's loaded template must still be usable by the receiver selected character through the same job/sex/empire/`min_level` guards already owned by `CanUseTemplate` (so a giver-legal display cannot finalize into a restricted receiver); the incoming displayed items must then fit the receiver's carried inventory under loaded templates (merging into compatible unlocked stacks first and otherwise requiring fresh carried slots); and incoming displayed gold must fit the receiver's current gold point-change carrier. Receiver item-id collision, over-template-max compatible-stack, inventory-capacity, gold-overflow, or receiver selected-character restriction failures reject the second accept silently with no self/peer accept marker, no result frame, no mutation, and the shell remains cancellable. When all revalidation passes, the requester receives one direct `GC::EXCHANGE ACCEPT` with `is_me = 1`, and the paired peer receives one queued `GC::EXCHANGE ACCEPT` with `is_me = 0`; both packets carry `arg1 = 1` and leave the remaining fields zero. When the requester's remembered displayed gold is now greater than current live gold, the requester instead receives one direct `GC::EXCHANGE LESS_GOLD`, no peer accept marker is queued, and the accepted marker is not changed. A first-side accept still leaves the shell open and cancellable. When the second side's accept also passes the frozen revalidation/precondition checks above, the bootstrap runtime now finalizes the currently displayed trade instead of remaining display-only:

- transfer each currently displayed carried item from its source character into the paired receiver using the same receiver placement rules already frozen by the second-accept inventory-capacity / compatible-stack precondition (merge into compatible unlocked stacks first, otherwise place into a fresh carried slot while preserving the displayed item identity). Locked compatible stacks are skipped for merge capacity exactly like pickup merge; if only locked compatible stacks remain and no free carried cell is available, the second-accept precondition fails closed with no frames and no mutation
- debit each side's currently displayed gold from the giver and credit it to the paired receiver through the owned gold point-change path
- clear any source item quickslots that pointed at transferred whole stacks using the already-owned quickslot deletion ordering, emitting self/queued `GC::QUICKSLOT_DEL` after that side's inventory refresh frames and before any gold `PLAYER_POINT_CHANGE` / shell `END` frames in the finalize burst
- persist both selected-character account snapshots after the live mutations succeed
- close the exchange shell immediately afterward with self `GC::EXCHANGE END` for the second accepter and one queued `GC::EXCHANGE END` for the first accepter

No richer finalize/result packet family is introduced in this slice. If either side's live state drifts after the second accept marker would otherwise pass, or if either persistence write fails (origin save or partner save, including the partner-save rollback of an already-written origin snapshot), the mutual-accept finalize fails closed with no trade mutation, emits no finalize/result frames, leaves live inventory/equipment/quickslot/gold state unchanged on both sides, and leaves the shell cancellable until a later slice owns stronger rollback/audit policy.

Commit-time revalidation is part of that same fail-closed finalize gate. After `AcceptExchange` returns a mutual-accept finalize plan, and before the shared-world commit applies live character updates, enqueues finalize/accept/`END` frames, or clears the shell, the runtime re-checks under the shared-world lock:

- neither paired side currently has an open merchant / safebox / refine busy presentation;
- both sides' remembered displayed items from the plan still match the current shared-world live characters and loaded templates;
- both sides' remembered displayed gold from the plan still fit each giver's current live gold;
- both receivers still satisfy the already-owned finalization preconditions against current shared-world live characters.

If any of those commit-time checks fail, finalize fails closed the same way: no durable trade mutation remains (account/live rollbacks already owned by the finalize apply path stay in force), no finalize/accept/`END` frames are emitted, and the shell stays cancellable. Commit-time busy-window drift is the one owned feedback exception: when the commit requester (`AcceptExchange` second accepter / `plan.OriginID`) currently has an open merchant / safebox / refine presentation, the runtime returns one self-only `CHAT_TYPE_INFO` with the same requester busy text already owned by exchange `START` / `ACCEPT` (`You cannot trade while another trade window is open.`); when only the paired partner is busy, it returns the same partner busy text (`That player cannot trade right now.`). When both sides are busy, the commit-requester busy text wins. Non-busy commit-time revalidation failures (displayed item/gold drift or receiver finalization precondition drift) stay silent/no-frame.

When an accepted shell receives a successful display-changing `ITEM_ADD`, `ITEM_DEL`, or in-budget `GOLD_ADD`, the runtime clears any previously displayed accept markers before the display-change frame. For the requester, a previously accepted requester side emits self `GC::EXCHANGE ACCEPT(is_me = 1, arg1 = 0)` and peer `GC::EXCHANGE ACCEPT(is_me = 0, arg1 = 0)`. A previously accepted partner side emits peer `GC::EXCHANGE ACCEPT(is_me = 1, arg1 = 0)` and self `GC::EXCHANGE ACCEPT(is_me = 0, arg1 = 0)`. The reset order is requester side first and then partner side when both were accepted, followed by the display-change frame for the receiver. These reset frames change only the in-memory/presentation accept markers; they still perform no item, gold, quickslot, ground-handle, or persisted-account mutation.

Unsupported or malformed `EXCHANGE` contexts still fail closed:

- no final result server frames are emitted; stale requester displayed items or displayed-item template metadata at accept time emit no frames, stale already-accepted partner displayed items, displayed-item template metadata, or gold also emit no frames on the second accept, receiver item-id collision, over-template-max compatible-stack, inventory-capacity, gold-overflow, or receiver selected-character restriction failures emit no frames on the second accept; either-side open merchant/safebox/refine busy-window precondition failures on `ACCEPT` / second accept emit only the self-only busy info-chat described above; commit-time busy-window drift after a second-accept finalize plan is built likewise emits only that same self-only busy info-chat for the commit requester while non-busy commit-time revalidation failures stay silent/no-frame; and the owned stale requester displayed-gold accept exception emits only the same self-only `LESS_GOLD` status frame already used by over-budget `GOLD_ADD`
- no carried inventory or equipment state is mutated
- no quickslots are added, deleted, or retargeted
- no points or gold are changed
- no temporary ground item handle is registered
- no peer-facing final result frames are queued
- no selected-character account snapshot is persisted

Once a selected character is already at the bootstrap zero-HP floor, new `START`, active-shell `ITEM_ADD`, `ITEM_DEL`, `GOLD_ADD`, `ACCEPT`, and `CANCEL` attempts fail closed with no exchange frames. If the zero-HP floor is reached while a shell is already open, the death-edge close above is the only owned post-floor exchange frame; later stale exchange requests then fail closed.

There is one owned guard-feedback exception for `ITEM_ADD`. When all of these are true:

- the selected character is already in `GAME` and above the bootstrap zero-HP floor
- the requester owns a live shared-world session that is already paired in the bootstrap exchange shell
- the exchange subheader is `ITEM_ADD`
- the source position is a carried inventory cell (`window = INVENTORY`, `cell < 90`)
- the requested exchange item display slot is in the current owned `0..11` range
- the carried item resolves through the loaded item-template snapshot
- the template `vnum` matches the carried item and validates normally
- the live carried item is unlocked, well-formed, unique in that carried cell, and its live count does not exceed `template.max_count`
- the template authors one owned exchange-display rejection guard (`anti_stack`, `anti_get`, `anti_drop`, `anti_give`, `anti_sell`, job/sex/empire anti flags, or `min_level`)
- the template authors non-empty `give_reject_message`

then the minimal runtime keeps the existing guard response instead of emitting `GC::EXCHANGE ITEM_ADD`, and returns one self-only `CHAT_TYPE_INFO` frame:

- `vid = 0`
- `message = template.give_reject_message`

That response is deliberately not an exchange-window item placement or transfer attempt and is available only inside an active paired shell. No-shell `ITEM_ADD` attempts remain ordinary no-frame/no-mutation rejections even when the carried template authors one of those guards plus `give_reject_message`. When the same template omits `give_reject_message`, the already-owned silent display-suppression path remains unchanged. The guard response still performs no inventory, equipment, quickslot, gold, ground-handle, peer, or persistence mutation.

Templates that author `give_reject_message` without one of those owned exchange-display rejection guards are invalid at the item-template store boundary, and embedded NUL bytes in the message fail closed before runtime boot.

Malformed `EXCHANGE` payload sizes fail at the codec/dispatcher boundary rather than reaching runtime mutation code.

## Deferred behavior

Later slices must write a new contract before broadening this packet into real gameplay. In particular, this slice does not freeze:

- richer trade target eligibility beyond the current visible-player check plus owned exchange-distance gate (`ApproxDistance < 1000`), the requester-side open-merchant / open-safebox / open-refine-dialog PREVENT_TRADE_WINDOW start reject, the partner-side open-merchant / open-safebox / open-refine-dialog busy-window rejection text, and the owned exact-position transfer / warp rebootstrap exchange teardown
- partner-side open player-shop / cube busy-window rejection text
- exchange-window item/gold/accept updates beyond the current `START` / display-only `ITEM_ADD` / display-only `ITEM_DEL` / display-only `GOLD_ADD` / display-only `ACCEPT` / accept reset / accept-time displayed-item and displayed-gold revalidation / `LESS_GOLD` / `END` shell
- trade item removal, carried-item locking/removal, or accepted gold mutation semantics beyond the first mutual-accept finalize described above
- real finalize/result state machines beyond the first mutual-accept mutation + shell-close contract
- two-party inventory/gold mutation ordering beyond the first mutual-accept finalize described above
- accepted anti-flag/template guard behavior inside an active exchange beyond the active-shell self-only transfer/selected-character `give_reject_message` `ITEM_ADD` rejection, the silent omit-text display suppression guards, and the second-accept receiver selected-character restriction precondition described above
- rollback, audit, or durable economic policy beyond the current fail-closed mutual-accept finalize

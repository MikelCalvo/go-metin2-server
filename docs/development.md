# Development

## Baseline

- Go 1.26
- two daemons: `authd` and `gamed`
- dedicated ops/pprof server per daemon
- Docker multi-stage build with lightweight runtime image

## Commands

```bash
make test
make build
```

`make build` stamps `internal/buildinfo` via `-ldflags` using a UTC RFC3339 build date plus `VERSION` / `COMMIT` resolved from `GITHUB_REF_NAME` / `GITHUB_SHA` when set, otherwise `git describe` / `git rev-parse` (fallbacks `dev` / `none`). Unstamped `go run` / plain `go build` binaries keep the package defaults (`dev` / `none` / `unknown`). See [release/versioning policy](workflow/release-versioning.md). For the first lab host layout, timestamped artifact trees, daemon JSON logging / secret-redaction conventions, and metadata-only loopback `/local/*` access logs, see [lab deployment topology](workflow/lab-deployment-topology.md) and [production observability](workflow/production-observability.md). Disabled-by-default FreeBSD `rc.d` / systemd samples for `authd` / `gamed` live under [`contrib/lab-daemons/`](../contrib/lab-daemons/) ([lab daemon unit samples](workflow/lab-daemon-unit-samples.md)), including optional `/var/log/metin2/{authd,gamed}.log` capture plus reviewable `newsyslog` / `logrotate` fragments ([JSON stdout capture plan](plans/2026-08-24-lab-daemon-json-stdout-capture.md)); offline `backup-restore-drill` / `migration-run-retention` printers optionally copy those logs into each retention tree ([CLI daemon log retention correlation](plans/2026-08-24-cli-daemon-log-retention-correlation.md)); print-only retention/GC unit samples remain under [`contrib/lab-retention-gc/`](../contrib/lab-retention-gc/).

Run locally:

```bash
go run ./cmd/authd
go run ./cmd/gamed
```

Inspect stamped identity after `make build`:

```bash
curl -sS http://127.0.0.1:6060/local/build-info
./bin/metin2-migrate version
```

## Docker

Build the default lightweight runtime image:

```bash
docker build --target runtime -t go-metin2-server:latest .
```

Or use the Makefile helper, which forwards the same `VERSION` / `COMMIT` / `BUILD_DATE` args used by local builds:

```bash
make docker-build
```

Build the debug-flavoured runtime image:

```bash
docker build --target runtime-debug -t go-metin2-server:debug .
```

The Dockerfile keeps debug information on purpose: the final image stays small, but DWARF/symbol data is preserved for better profiling and stack analysis.

## Public CI

The repository ships with a GitHub Actions baseline workflow in `.github/workflows/ci.yml`.

It currently validates:

- `gofmt` cleanliness
- `go test ./...`
- `go vet ./...`
- daemon builds for `authd`, `gamed`, and `metin2-migrate`
- Docker runtime and debug image builds

Binary and image builds stamp `internal/buildinfo` when invoked through `make build` / `make docker-build`. The public CI workflow prefers `GITHUB_SHA` (first 12 chars) and `GITHUB_REF_NAME` for those stamps, reuses the same resolved identity for Go and both Docker targets, and fail-closes when `GITHUB_SHA` is set but the stamped `metin2-migrate version` commit is blank/`none` or mismatches the resolved value. Docker images additionally stamp OCI / Actions workflow-run labels (`org.opencontainers.image.{version,revision,created}`, `com.github.actions.run_{id,attempt}`) from the same identity plus optional `GITHUB_RUN_ID` / `GITHUB_RUN_ATTEMPT`; CI asserts those labels after each image build. Process `/local/build-info` and `metin2-migrate version` stay metadata-only (`version` / `commit` / `build_date`) and do not carry workflow-run IDs.

The intent is simple: every small slice should be pushable and publicly re-checkable.

## Runtime configuration

### pprof / local ops

- `authd`: `METIN2_AUTHD_PPROF_ADDR` (default `127.0.0.1:6061`)
- `gamed`: `METIN2_GAMED_PPROF_ADDR` (default `127.0.0.1:6060`)
- global override: `METIN2_PPROF_ADDR`

The ops listener also carries loopback-only recovery/debug endpoints under `/local/*`, so startup rejects wildcard or non-loopback pprof binds such as `:6060`, `0.0.0.0:6060`, `[::]:6060`, or a remote hostname. If remote profiling is needed, keep the daemon bound to loopback and use an SSH tunnel or another explicit local transport instead of exposing the ops mux directly.

### Legacy TCP listeners

- `authd`: `METIN2_AUTHD_LEGACY_ADDR` (default `:11002`)
- `gamed`: `METIN2_GAMED_LEGACY_ADDR` (default `:13000`)
- global override: `METIN2_LEGACY_ADDR`

### Advertised public host

- default: `127.0.0.1`
- `authd`: `METIN2_AUTHD_PUBLIC_ADDR`
- `gamed`: `METIN2_GAMED_PUBLIC_ADDR`
- global override: `METIN2_PUBLIC_ADDR`

`gamed` currently advertises `PublicAddr + port(LegacyAddr)` in `LOGIN_SUCCESS4`.

### Bootstrap visibility policy

`gamed` defaults to whole-map bootstrap visibility: connected players and static actors share visibility when they are in the same effective `MapIndex` on the local bootstrap channel.

The runtime can opt into the radius AOI policy with environment overrides:

- `METIN2_VISIBILITY_MODE` / `METIN2_GAMED_VISIBILITY_MODE`
  - default: `whole_map`
  - supported values: `whole_map`, `radius`
  - values are normalized by trimming whitespace, lowercasing, and treating `-` as `_`
- `METIN2_VISIBILITY_RADIUS` / `METIN2_GAMED_VISIBILITY_RADIUS`
  - required positive integer when `visibility_mode = radius`
- `METIN2_VISIBILITY_SECTOR_SIZE` / `METIN2_GAMED_VISIBILITY_SECTOR_SIZE`
  - required positive integer when `visibility_mode = radius`

Service-specific overrides take precedence over global overrides for each field. Invalid visibility mode or non-positive radius/sector values fail `gamed` startup instead of falling back silently.

Use the loopback-only `GET /local/runtime-config` endpoint to confirm the policy the running `gamed` process actually booted with.

### Bootstrap persistence paths

The file-backed bootstrap stores can now be pointed at explicit paths without changing code. Service-specific overrides take precedence over the global value for each store, matching the existing address and visibility configuration rules:

- login-ticket handoff store directory:
  - `METIN2_LOGIN_TICKET_STORE_DIR`
  - `METIN2_AUTHD_LOGIN_TICKET_STORE_DIR`
  - `METIN2_GAMED_LOGIN_TICKET_STORE_DIR`
- durable account snapshot store directory:
  - `METIN2_ACCOUNT_STORE_DIR`
  - `METIN2_AUTHD_ACCOUNT_STORE_DIR`
  - `METIN2_GAMED_ACCOUNT_STORE_DIR`
- authored static-actor snapshot path:
  - `METIN2_STATIC_ACTOR_STORE_PATH`
  - `METIN2_GAMED_STATIC_ACTOR_STORE_PATH`
- authored interaction-definition snapshot path:
  - `METIN2_INTERACTION_STORE_PATH`
  - `METIN2_GAMED_INTERACTION_STORE_PATH`
- authored item-template snapshot path:
  - `METIN2_ITEM_TEMPLATE_STORE_PATH`
  - `METIN2_GAMED_ITEM_TEMPLATE_STORE_PATH`
- pending ground-item snapshot path:
  - `METIN2_GROUND_ITEM_STORE_PATH`
  - `METIN2_GAMED_GROUND_ITEM_STORE_PATH`
- durable safebox snapshot path:
  - `METIN2_SAFEBOX_STORE_PATH`
  - `METIN2_GAMED_SAFEBOX_STORE_PATH`

Default paths remain under the process temp directory with dedicated parents for each file-backed store (`go-metin2-server-login-tickets`, `go-metin2-server-accounts`, `go-metin2-server-static-actors/static-actors.json`, `go-metin2-server-interaction-definitions/interaction-definitions.json`, `go-metin2-server-item-templates/item-templates.json`, `go-metin2-server-quest-state/quest-state.json`, `go-metin2-server-ground-items/ground-items.json`, and `go-metin2-server-safebox/safebox.json`) so local bootstrap runs remain zero-config and restore-safe. For persistent QA runs or backup/restore drills, set explicit store directories/paths before starting both daemons; `authd` and `gamed` must share the same login-ticket and account-store locations when exercising the one-shot ticket handoff.

Startup now validates the effective bootstrap persistence layout before daemon runtime wiring. On `authd`, the login-ticket and account-store paths must both be non-empty directory stores, must not point at existing regular files, must not be symlink roots, and must not overlap, so issuing a login key cannot accidentally write into the same tree as durable account snapshots. On `gamed`, directory-backed stores (`login_ticket_store_dir`, `account_store_dir`) must be non-empty, must not point at existing regular files, must not be symlink roots (including dangling symlinks), and must own distinct directory trees; file-backed stores (`static_actor_store_path`, `interaction_store_path`, `item_template_store_path`, `quest_state_store_path`, `ground_item_store_path`, `safebox_store_path`) must be non-empty, must not point at existing directories, must not share the same file path, must not share a parent directory with another file-backed store, and must not live inside either directory-backed store. Shared parents fail closed because restore empties `filepath.Dir(snapshotPath)` and would wipe sibling snapshots/manifests. The overlap / shared-parent checks use cleaned absolute paths, lexical path placement, and existing symlink resolution for the file-backed stores, while directory-backed store roots are required to be direct filesystem directories so backup, restore, cleanup, and ticket-consume directory syncs cannot silently operate through an alias outside the operator-visible store boundary.

`GET /local/runtime-config` includes the active persistence paths under `persistence`, so local operators can verify which JSON stores a running `gamed` instance will validate, back up, restore, or mutate before invoking the local-only persistence endpoints. Pending bootstrap ground item/gold handles rematerialize from the ground-item FileStore across `gamed` process restart, and the combined backup/restore drill covers `BackupTo` / `RestoreFrom` through `/local/ground-item-store/*` (restore also rematerializes the live shared-world pending set). Durable safebox cells rematerialize from the safebox FileStore across restart/reconnect, and the same drill now also covers `/local/safebox-store/*` (see [safebox file-store backup/restore drill fold-in](plans/2026-08-23-safebox-file-store-backup-restore-drill.md)).

### Database migration preflight config

The database-backed runtime is still future work, but `gamed` can now point the read-only migration-status preflight at an explicitly configured `schema_migrations` ledger through `database/sql`:

- `METIN2_DB_DRIVER`
- `METIN2_GAMED_DB_DRIVER`
- `METIN2_DB_DSN`
- `METIN2_GAMED_DB_DSN`

Both driver and DSN must be empty to keep DB preflight disabled, or both must be set. Partial values fail daemon startup instead of silently returning the embedded empty-ledger migration plan. `cmd/metin2-migrate` is the first shipped migration CLI. Its catalog, status, empty-ledger-snapshot, ledger-snapshot, ledger-snapshot-status, plan, plan-artifact, plan-artifact-status, apply-preflight, apply-preflight-status, apply-lock-status, apply-audit-status, import-export-status, quarantine-export, export-quarantine-drill, backup-restore-drill, migration-run-retention, and artifact-retention-gc commands are read-only/preflight/print-only surfaces. `artifact-gc-aside-purge` is a confirmation-gated print-only companion that emits a shell script for deleting aged `.gc-aside-*` trees (CLI still never executes that purge). `import-export-drill` is a confirmation-gated print-only companion that emits a shell script walking a retained export/quarantine tree into `import-export` plus matching `import-export-status` redirects (CLI still never executes that import, never embeds a DSN value, and never opens a database). `apply-lock-aside` is a separate confirmation-gated local filesystem mutation for lab stale-lock recovery and still never opens a database. `import-export` is a confirmation-gated CLI-only SQL import mutation for retained migration-shaped exports (see below):

`apply-lock-status` is the read-only lock-triage companion for `apply --lock-file`: it reads a non-symlink regular metadata-only `go-metin2-migration-apply-lock-v1` file with a 16 KiB cap, returns `present: false` when the path is absent, and returns `go-metin2-migration-apply-lock-status-v1` JSON for valid locks without opening the database target, deleting the lock file, or exposing DSNs / executable SQL. Present locks also include advisory `holder_pid_alive` / `holder_pid_check=local_signal_0` fields from a local signal-0 probe against `lock.pid`, advisory `holder_hostname_local` / `holder_hostname_check=local_os_hostname` from comparing `lock.hostname` to the inspecting host's `os.Hostname()`, advisory `holder_build_matches` / `holder_build_check=local_buildinfo_current` from comparing stamped `build_version` / `build_commit` / `build_date` to `buildinfo.Current()` on the inspecting binary, advisory `lock_age_seconds` / `lock_age_check=local_wall_clock` as the non-negative whole-second floor of wall-clock age since `lock.created_at` (future-dated locks clamp to `0`), and advisory `manual_clear_candidate` / `manual_clear_check=lab_stale_lock_policy_v1` (`true` only when PID is absent, hostname is local, build identity matches, and age is at least 3600 seconds). A false liveness/locality/build-match result or a true candidate is triage evidence only and never authorizes automatic lock deletion; on the single-host lab topology follow [lab stale-lock recovery](workflow/lab-stale-lock-recovery.md) for aside-rename recovery after operator judgment.

`apply-lock-aside` is the confirmation-gated lab recovery companion for leftover `apply --lock-file` artifacts: it requires `--i-confirm-lab-aside-rename`, recomputes the same `lab_stale_lock_policy_v1` gate used by `apply-lock-status`, renames the lock to `<path>.stale-<UTC>` only when the candidate gate still holds, refuses destination collisions, never unlinks/`rm`s the lock, never opens a database target, and emits metadata-only `go-metin2-migration-apply-lock-aside-v1` JSON. A true `manual_clear_candidate` alone is not enough; follow [lab stale-lock recovery](workflow/lab-stale-lock-recovery.md).

`quarantine-export` is the offline companion to the loopback `POST .../quarantine` endpoints: it validates and canonicalizes a retained migration-shaped export from a regular non-symlink file or stdin, using `--kind` values `account-character-roster`, `character-item-state`, `character-point-state`, `character-quest-state`, `auth-login-ticket-handoff`, `item-template-state`, `static-actor-content-state`, `bootstrap-ground-item-state`, and `character-safebox-state`. Input is capped at 1 MiB, must be valid UTF-8, and must decode with unknown fields disallowed. Successful stdout is the same `{ "summary": ..., "export": ... }` JSON shape returned by the loopback quarantine handlers; contract failures exit `1` with stderr only. The command never opens a database, writes store snapshots, emits SQL/DSN text, or mutates live runtime state. Hermetic loopback `GET .../exports/<kind>` → retained-file → offline `quarantine-export` coverage for roster plus tip-`0015` safebox money is owned by [hermetic export → offline quarantine-export CLI proof](plans/2026-08-25-hermetic-export-quarantine-offline-cli-proof.md); those export/quarantine routes are registered through `minimal.RegisterGamedMigrationQuarantineExportOps`.

`import-export` is the confirmation-gated CLI mutation companion for the same kind vocabulary: it requires `--driver` / `--dsn` / `--i-confirm-sql-import`, re-validates the retained export through the existing quarantine contracts before `sql.Open`, and dispatches to the landed programmatic `Import*` seams (insert-only, no upsert, no stock production driver, no daemon mutation route). Successful stdout is the metadata-only `Import*Result` JSON already owned by each seam; DSNs are redacted from stderr. See [CLI import-export](plans/2026-08-27-cli-import-export.md).

`import-export-status` is the read-only inspection companion for retained `import-export` result files (`import-result.json`): it requires `--kind` plus `--import-result`, returns `present: false` when the path is absent, and returns `go-metin2-import-export-status-v1` JSON with the exact result checksum plus the decoded tip-kind `Import*Result` when the file is a valid non-symlink regular artifact under the 128 KiB cap. Tip identity, non-negative counts, and identity-slice length checks fail closed; the command never opens a database, never re-runs import, and never emits DSNs / executable SQL. See [CLI import-export status](plans/2026-08-28-cli-import-export-status.md).

`import-export-drill` is the confirmation-gated print-only companion for walking a retained `export-quarantine-drill` tree into `import-export`: it requires an absolute `--export-tree`, an opaque `--driver` name literal, and `--i-confirm-print-sql-import-drill`, then prints a shell script that reads the import DSN only from `--dsn-env` (default `METIN2_IMPORT_DSN`), fail-closes when each `$EXPORT_TREE/<kind>/quarantine.json` is missing, invokes `metin2-migrate import-export ... --i-confirm-sql-import` for every tip kind in fixed order, and redirects a matching `import-export-status` inspection beside each `import-result.json`. The printer never executes the imports, never opens a database, and never embeds a DSN value or executable SQL. Automatic / scheduled execution, stock production-driver registration, and upsert policy remain deferred.
```bash
go run ./cmd/metin2-migrate apply \
  --driver <database/sql-driver> \
  --dsn <dsn> \
  --ledger-snapshot snapshot.json \
  --target-version 0 \
  --apply-preflight rollback-apply-preflight.json \
  --lock-file migration-apply.lock \
  --audit-file migration-rollback-audit.json \
  --allow-rollback
```

`apply` requires an operator-supplied `database/sql` driver name, DSN, strict offline ledger snapshot, and target version. It reuses `db/migrations.ApplyToVersion`, so pending up/down migration statements run inside one transaction and the transaction-local `schema_migrations` ledger is re-verified before commit when applicable. Successful output is metadata-only `ApplyResult` JSON; executable SQL and DSNs are not printed, and the supplied DSN is redacted from apply errors. Any plan containing down/rollback steps is rejected before opening the database unless the operator passes both `--allow-rollback` and an exact plan confirmation (`--plan-sha256 <hex>`, `--plan-artifact <path>`, or `--apply-preflight <path>`). The flag is intentionally required in addition to the numeric target, and the plan confirmation is intentionally required in addition to the direction acknowledgement, so rollback cannot happen from a mistyped target or an unreviewed down plan. Operators may pass exactly one of `--plan-sha256 <hex>`, `--plan-artifact <path>`, or the stricter runbook handoff `--apply-preflight <path>` to require that the metadata-only dry-run plan recomputed from the supplied ledger snapshot and target matches previously inspected evidence before the CLI opens the database; combining confirmation sources is a usage error. The plan-artifact path validates the strict `go-metin2-migration-plan-artifact-v1` shape with a 128 KiB input cap, rejects oversized/malformed/trailing JSON and internally inconsistent checksums, and requires the embedded plan plus `plan_sha256` to match the requested apply boundary. The apply-preflight path validates the strict `go-metin2-migration-apply-preflight-v1` shape and additionally requires the retained preflight ledger checksum, resolved target, plan checksum, and embedded plan to match the supplied apply ledger snapshot and target. Operators may pass `--lock-file <path>` to reserve an exclusive local filesystem lock after plan/artifact validation and before opening the DB target; an existing lock file fails closed before mutation, and a reserved lock is removed on success or failure. While reserved, the lock contains metadata-only `go-metin2-migration-apply-lock-v1` JSON with local PID, hostname, stamped `build_version` / `build_commit` / `build_date`, target, ledger-snapshot checksum, plan checksum, and optional confirmed plan/preflight checksum; it never contains the DSN or executable SQL. Operators may also pass `--audit-file <path>` to write a metadata-only `go-metin2-migration-apply-audit-v1` JSON artifact with the applied result, resolved target, configured driver name, DSN-present boolean, confirmed plan checksum when provided, and SHA-256 of the exact offline ledger snapshot; the audit file is created exclusively, never overwrites an existing file, rejects no-op apply plans, and is removed if apply fails before the audit can be committed. The lock file is not a distributed mutex or stale-lock policy yet; it is a local single-run guard for the first production runbooks. The command is not a daemon endpoint, not an auto-migration hook, not a backup/restore mechanism, and not proof that runtime stores are DB-backed. Production use still needs an explicit driver/engine choice in the build, backup/restore runbook, and deployment coordination before real rollout.

`db/migrations` also exposes the same apply primitive for future repository work. `ApplyCatalogUpToVersion` validates the same catalog/ledger/target boundary used by dry-run planning, executes pending up and down migration statements inside one transaction, writes or deletes matching `schema_migrations` rows, verifies transaction-local ledger state before commit when applicable, and rolls the transaction back on SQL, ledger, row-count, verification, or commit failures. This primitive and the CLI are deliberately not registered as local ops endpoints and are not wired into daemon startup.

### Bootstrap file-backed persistence

The current bootstrap runtime uses several small JSON-backed stores before a compatibility-grade database exists:

- `internal/accountstore` stores durable account snapshots.
- `internal/loginticket` stores one-shot authd-to-gamed login tickets.
- `internal/staticstore` stores authored bootstrap static-actor snapshots.
- `internal/interactionstore` stores authored bootstrap interaction definitions.
- `internal/itemstore` stores authored bootstrap item-template snapshots used by content bundles, merchant previews, and item/equipment runtime policy.

The bootstrap file stores intentionally fail closed on unknown top-level JSON fields and trailing JSON values. The account store validates the persisted login identity, rejecting empty, whitespace-padded, or mismatched snapshot logins instead of trusting only the filename, and validates persisted character identity plus item/equipment/quickslot payloads before accepting a snapshot. Character identity validation requires non-zero character records to carry non-empty, unpadded names and treats repeated all-zero character records as intentional empty select-screen slots, while rejecting any zero-ID slot that still carries non-empty name, VID, location, stats, guild, gold, item, equipment, or quickslot state so deleted-slot residue cannot masquerade as either a real character or a reusable empty slot. Its deterministic account listing boundary scans only committed canonical lowercase hex-login `.json` snapshots, ignores leftover hidden temp files from interrupted writes, returns missing directories as an empty store, sorts by normalized login, and fails closed on symlinked, corrupt, filename-mismatched, non-canonical, or case-variant duplicate committed snapshots. The login-ticket store uses the same strict decode and character payload validation boundary for ticket files: empty or whitespace-padded logins, zero login keys, filename/login-key drift, duplicate non-zero character IDs/names, blank or whitespace-padded non-zero character names, non-empty zero-ID character slots, malformed inventory, duplicate equipment slots, and malformed quickslots return `ErrInvalidTicket`, and a failed consume leaves the ticket file in place for inspection instead of deleting possibly corrupted handoff state. Its deterministic ticket validation boundary scans only committed canonical lowercase 8-digit hex login-key `.json` snapshots, ignores leftover hidden `.ticket-*.json` temp files, returns missing directories as an empty store, sorts by normalized login and login key, rejects symlinked committed ticket snapshots before decoding, and never consumes ticket... [truncated]

Account snapshot writes are committed through same-directory temp files, synced before rename, and followed by a directory sync after rename. Login-ticket issue writes follow the same temp-file sync boundary, then publish the ticket with an exclusive same-directory link so a ticket that appears after the preflight existence check is not overwritten; the store directory is synced after the ticket becomes visible. Destructive login-ticket consumes also sync the store directory after deleting the consumed ticket, so successful authd-to-gamed handoff removal is part of the crash-safety boundary instead of only the issue/write path. Account-listing behavior therefore matches that crash-safety model: incomplete `.account-*.json` temp files are not treated as restorable accounts, while malformed committed snapshots stop the listing so future backup/migration tooling cannot silently skip bad durable state. This makes the current JSON stores more crash-tolerant on normal local filesystems while preserving the intentionally simple bootstrap format.

Committed account gold/inventory and quest-flag snapshots rematerialize across a `gamed` process restart from the same FileStore paths: login prefers the account-store roster over a stale login-ticket character snapshot, so a successful `quest_flag` reward turn-in survives daemon restart without depending on ticket payload freshness. The focused proof is `TestGameRuntimeQuestFlagRewardStateRematerializesAcrossDaemonRestart` in [character-state process-restart recovery](plans/2026-08-20-character-state-process-restart-recovery.md). Pending bootstrap ground-item / ground-gold handles likewise rematerialize from the dedicated ground-item FileStore (`METIN2_GROUND_ITEM_STORE_PATH` / `METIN2_GAMED_GROUND_ITEM_STORE_PATH`, default `$TMP/go-metin2-server-ground-items/ground-items.json`) across `gamed` process restart, with absolute ownership/despawn timers and identity-keyed exclusive ownership when process-local `OwnerID` is gone; the focused proof is `TestGameRuntimePendingGroundItemAndGoldRematerializeAcrossDaemonRestart` in [ground-item process-restart durability](plans/2026-08-22-ground-item-process-restart-durability.md). Operators preserve those durable handles through the ground-item store in [file-store backup/restore drill](workflow/file-store-backup-restore-drill.md) via `/local/ground-item-store/*` (see [ground-item file-store backup/restore](plans/2026-08-22-ground-item-file-store-backup-restore.md)). Durable safebox cells rematerialize across `gamed` process restart / reconnect from the dedicated safebox FileStore and are preserved as the eighth store in the same drill via `/local/safebox-store/*` (see [safebox file-store backup/restore drill fold-in](plans/2026-08-23-safebox-file-store-backup-restore-drill.md) and [durable safebox persistence contract freeze](plans/2026-08-22-durable-safebox-persistence-contract-freeze.md)).

The account store also has narrow backup and restore primitives for future operator/migration tooling. `FileStore.BackupTo(dstDir)` validates the source through the same deterministic `List()` path, copies only committed snapshots into an empty destination directory outside the active account-store directory, omits crash temp files, and fails closed if any committed source snapshot is corrupt or filename-mismatched. It also writes a deterministic `account-backup-manifest.json` containing the backup format string, copied snapshot summary, per-account filenames, byte sizes, and SHA-256 checksums so operators have a stable audit artifact before restore/migration work. When the active account store already contains restored backup metadata, `BackupTo` validates that active manifest before creating the destination and fails closed on stale or malformed manifest state, so an operator cannot mint a new backup from a store whose own restored-backup marker no longer matches the committed account files. `FileStore.RestoreFrom(srcDir)` and `FileStore.ValidateBackupFrom(srcDir)` now require that manifest before accepting a source directory, apply the same committed-snapshot validation before restore/preflight, ignore the manifest as metadata rather than an account snapshot, reject symlinked manifests, manifested account snapshots, or crash-temp-shaped entries, ignore regular-file crash temp residue as restorable payload while reporting it in dry-run backup summaries, reject crash-temp-shaped directories as untracked backup entries, reject a missing restore source or missing manifest explicitly, and refuse to merge restore output into a non-empty destination. Both sides require an empty destination so operator recovery cannot silently blend stale files with a validated snapshot set, backups refuse `dst_dir` values that lexically or symlink-resolve equal to or nested under the live store so the backup scan cannot copy its own in-progress output, restores refuse destinations that lexically or symlink-resolve equal to or nested under the backup source so recovery cannot write into the source tree being verified, manifest file entries must preserve the exact committed snapshot login casing instead of only matching case-insensitively, manually assembled snapshot directories must first be converted into a real backup with a manifest before they can be restored, committed-copy/manifest-write/final-sync failures roll back files already written into the destination, and later normal account saves remove restored manifest metadata before syncing so mutated live state cannot keep claiming exact backup equivalence.

The login-ticket store now mirrors that narrow backup/restore posture for the one-shot authd-to-gamed handoff set. `loginticket.FileStore.BackupTo(dstDir)` validates the source through the same deterministic `List()` path, copies only committed tickets into an empty destination directory outside the active login-ticket store, omits crash temp files, and fails closed if any committed source ticket is corrupt or filename-mismatched. It also writes a deterministic `login-ticket-backup-manifest.json` containing the backup format string, copied ticket summary, per-ticket filenames, login keys, byte sizes, and SHA-256 checksums. When the active login-ticket store already contains restored backup metadata, `BackupTo` validates that active manifest before creating the destination and fails closed on stale or malformed manifest state. `FileStore.RestoreFrom(srcDir)` and `FileStore.ValidateBackupFrom(srcDir)` require that manifest before accepting a source directory, apply the same committed-ticket validation before restore/preflight, ignore the manifest as metadata rather than a ticket snapshot, reject symlinked manifests, manifested ticket snapshots, or crash-temp-shaped entries, ignore regular-file crash temp residue as restorable payload while reporting it in dry-run backup summaries, reject a missing restore source or missing manifest explicitly, and refuse to merge restore output into a non-empty destination. ## Legacy session runtime hooks

The legacy TCP runtime supports two optional per-session hooks:

- `FlushServerFrames() ([][]byte, error)` — allows a session flow to emit server-initiated frames even when no new client packet has arrived yet
- `io.Closer` — allows a session flow to release shared runtime state when the TCP session ends

The runtime checks for pending server frames between client reads.
